## PartnerCenterBridge v0.9.0

This release lands the Ops Workbench: a real navigation shell, a person-centric workspace,
policy-driven offboarding, Access Parity, and a first-class signed Local Workbench build. It
also brings up the automated release pipeline this release itself was built and published by.

### Local Workbench: signed exe

`PartnerCenterBridge.exe` -- one self-contained file, SQLite, local accounts, no server to stand
up -- is now Authenticode-signed with Azure Artifact Signing, using the same signing setup
already running for SpoolSmith. Windows should no longer flag it as an unknown publisher.
Verify a download with `Get-AuthenticodeSignature`, or check the zip's `.sha256` sidecar; see
"Checksum verification" below and `docs/code-signing.md`.

### New navigation

Tabs are real routes now (`/people`, `/people/:tenantId/:userId`, `/tenants`,
`/operations/*`, `/activity`, `/settings/*`, ...), wired through the router instead of
component-swap state -- browser history, deep links, and refresh/back/bookmark all work. A
six-area navigation (Home / People / Tenants / Operations / Activity / Settings) replaces the
previous tab set, and a keyboard-first command palette is available from anywhere in the shell.

### Person workspace

A single read brings together everything about one person in one tenant: profile, licenses,
group memberships, auth methods, mailbox, devices, and recent operation history, with
per-section gated actions. Reachable from People search or directly by tenant/user id.

### Access Parity

Copies a source user's missing cloud group memberships (security groups, mail-enabled security
groups, and directory role assignments) to a target user, additive-only -- it never removes
anything the target already has. The planner previews exactly what is missing before anything is
applied, reports unfulfilled selections honestly, and treats an already-current target as
"no change needed" rather than a failure. It does not compare SharePoint direct (non-group) site
or file permissions -- see Known limitations.

### Offboarding policy v2

Per-contract offboarding policy (block sign-in, revoke sessions, group cleanup, license removal,
mailbox conversion, forwarding, follow-up) with an ordered plan/apply/verify loop and structured
ticket evidence on every run. Highlights:

- **License-before-conversion ordering.** When a shared-mailbox conversion is requested, license
  and group removal now wait until that conversion is verified, instead of racing it -- removing
  a license before Exchange finishes converting the mailbox could otherwise leave it half
  configured.
- Device retire, inherited-license, and exact-forwarding verification all check the specific
  state Microsoft reports back, rather than assuming a requested change took effect.
- Verification that is interrupted (a crash, a lost connection, a cancelled run) keeps the
  evidence gathered so far and records in-flight actions as attempted, rather than discarding
  the run.
- A wrongly-optimistic outcome no longer claims changes were applied when only acceptance is
  known: `CompletedUnverified` now reads "Microsoft accepted the requested changes, but PCB
  could not confirm their effect yet" everywhere it's shown (server evidence and the web
  summary), and a pending device retire is described as requested, not completed.

### Evidence and ticket notes

Every planned operation (Access Parity, offboarding) records preflight findings, the plan, the
changes attempted, and verification results as structured evidence, plus a server-generated
`ticketNotes` narrative you can paste straight into a ticket. Evidence exports as JSON or
Markdown (`?format=markdown`) from `GET /api/workflows/runs/{id}/evidence`.

### First run and diagnostics

A fresh Local Workbench points its first administrator straight at connecting Microsoft and
adding tenants. The built-in `doctor` command (also `GET /api/system/diagnostics`) checks
Exchange Online PowerShell availability and SAM/Windows integration and reports what is and
is not configured, without treating either as fatal by itself.

### Local Workbench: optional no-account first run

On a machine that's already secured (screen lock, disk encryption, no shared Windows account),
first run can now skip account creation entirely: **Skip -- use without an account on this
computer** creates a built-in workbench owner with instance Administrator rights (and no tenant
access until it adds one), signed in through a single-use launch link minted by the running exe.
The link expires after two minutes; run the exe again for a fresh one. **Protect with an
account** from Settings > Account & security sets an email and password and turns it into
an ordinary Local account. Until then, self-registration, password login, passkeys, and TOTP are
all blocked for that account (MCP access tokens are not). With `--no-browser`, the launch link is
printed to the console instead of being opened, and never written to the log file. First-run
registration also requires a single-use setup link from the exe. A second launch gets a fresh
link only through a verified current-user named pipe, and conversion to an account revokes
earlier sessions and MCP tokens. This option is
never offered outside the Local Workbench, and first run refuses it outright -- not just hides it
-- when started with a non-loopback `--listen` address.

### Exchange Online hardening

Two security fixes to the Exchange Online path, plus a new configuration option:

- **Exchange is now bound to the tenant's Entra id.** The organization to connect to is resolved
  from Microsoft Graph (the tenant's verified initial `*.onmicrosoft.com` domain, cross-checked
  against its Entra tenant id) instead of the tenant's display `DefaultDomain`, and cached on the
  tenant. If the Exchange connection ever reports a different organization than expected, the
  operation is refused and nothing is changed.
- **The PFX password no longer touches disk.** It now reaches `pwsh` only over standard input,
  never written to a temporary file or passed on the command line.
- **New: `Exchange:CertificateThumbprint`.** On Windows, point at a certificate already imported
  (with its private key) into `Cert:\CurrentUser\My` or `Cert:\LocalMachine\My` instead of a PFX
  file -- no certificate secret is handled by the app at all. This is now the preferred option on
  Windows; `Exchange:CertificatePath` (+ `Exchange:CertificatePassword`) still works when set.

### CI and release automation

- `.github/workflows/ci.yml` gates every PR and push to `main`: the full xUnit suite (including
  Postgres-backed concurrency tests), the SPA type-check/test/build, a Windows job that publishes
  and smoke-tests the Local Workbench exe, and both container image builds.
- `.github/workflows/release.yml` is new: pushing a `vX.Y.Z` tag runs the same CI gate, then
  builds, signs, smoke-tests and packages the Windows exe, builds and pushes both container
  images, creates the GitHub release from `releases/vX.Y.Z.md`, and deploys the docs site to
  GitHub Pages -- all from one tag push. `workflow_dispatch` with `dry_run: true` (the default)
  runs the same pipeline without publishing anything, so a broken signing credential or a
  packaging regression shows up on a manual run, not on tag day.
- `.github/workflows/pages.yml` redeploys the docs site on its own, for a doc-only fix that
  doesn't warrant a full release.

See `CLAUDE.md`'s Release checklist for the operator-facing steps.

### Upgrade notes (server / container)

- The `OperationEvidence` table migration applies automatically at startup, the same as every
  other migration -- nothing to run by hand.
- New optional endpoints (`/api/people/...`, `/api/operations/...`, `/api/workflows/runs/...`)
  appear alongside the existing ones; nothing already in use changes shape.
- Nothing in `docker-compose.ghcr.yml` or `docker-compose.yml` needs to change -- pull the new
  image tags and restart.
- Two new nullable columns on `Tenant` (`ExchangeOrganization`, `ExchangeOrganizationVerifiedAt`)
  and two on `AppUser` (`IsWorkbenchOwner`, `SessionEpoch`) are added by migrations that apply automatically at
  startup, same as always -- nothing to run by hand. Existing tenants resolve their Exchange
  organization from Microsoft Graph the first time an Exchange operation runs against them, then
  cache it; `IsWorkbenchOwner` stays false for every existing account and has no effect on the
  Server profile, which never offers the no-account option.

### Known limitations

- No live-tenant validation of this branch has been done yet; testing so far is against WireMock
  and the mocked dev server.
- Mailbox-related fixes and offboarding steps that touch Exchange (mailbox archive repair,
  shared-mailbox conversion, forwarding) need Exchange Online PowerShell configured; without it,
  those steps report `Unavailable` with the reason rather than silently skipping.
- Access Parity and offboarding compare group memberships and directory roles only --
  SharePoint direct (non-group) site and file permissions are not compared or copied.
- The MCP `remediate_workflow` approval queue re-plans at approval time, applying whatever is
  eligible then rather than pinning the exact item set an approver previewed. For an
  additive-only operation like Access Parity the blast radius of that gap is small, but it is
  not yet fixed.

### Checksum verification

```powershell
(Get-FileHash PartnerCenterBridge-v0.9.0-win-x64.zip -Algorithm SHA256).Hash.ToLower()
Get-Content PartnerCenterBridge-v0.9.0-win-x64.zip.sha256
```

```sh
sha256sum -c PartnerCenterBridge-v0.9.0-win-x64.zip.sha256
```

Both should report a match. To also check the exe's signature:

```powershell
Get-AuthenticodeSignature .\PartnerCenterBridge.exe | Format-List Status, SignerCertificate, TimeStamperCertificate
```
