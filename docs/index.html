The same fix. Every tenant.
Once.

Your team already knows the fixes. Partner Center Bridge turns them into named, recorded actions. Known-fix workflows diagnose, fix, and verify one person's problem in one tenant, showing every step. App deploys push a Win32 package, and later its updates, out to the customer tenants on a contract. It runs on your own infrastructure, on top of Microsoft Graph, Partner Center, and Exchange Online.

Who it's for

MSP technicians who work across many customer tenants.

If you support dozens of Microsoft 365 customers, most tickets aren't hard. They're the same few problems, spread across dozens of tenants and admin portals.

  • One portal at a time

    Partner Center lists your customers, but finding a person or checking an app still means opening each tenant's admin portal separately.

  • Fixes repeated by hand

    The same MFA reset or app update gets clicked through tenant by tenant, and each technician does it a little differently.

  • Little evidence afterwards

    When the ticket closes, the only record of what was checked and changed is whatever someone typed into the notes.

How it works

Connect, define, then act.

Three steps from a list of customers to repeatable work you can review later.

  1. 1

    Connect your tenants

    Sync customers from Partner Center. The bridge reaches each tenant through your GDAP relationship and a multi-tenant app under the Secure Application Model. Nothing is installed in the tenant.

    Connect real tenantsSAM bootstrap

  2. 2

    Define contracts

    A contract is a named group of tenants and the Win32 apps they should have, plus new-hire provisioning defaults. Its plan shows, as a dry run, which tenants need a deploy, an update, or a retry.

    The contract model

  3. 3

    Deploy, or diagnose, fix and verify

    Push an app package to the tenants you pick, or run a known fix for one person. Every run is recorded: who ran it, against which tenant, what it found, and what it changed.

What's real today

Maturity, feature by feature.

What ships in v0.8.0 and how far along each piece is.

Stable

Win32 apps across tenants

Upload an .intunewin template once; the bridge runs Intune's documented beta upload sequence in each tenant you select. A redeploy updates the app in place: the new package plus the template's command lines and detection rules. The tenant's assignments, including changes made in the Intune portal, are left untouched.

In-place update behavior is tested against mocked Graph; it has not yet run against a live tenant.

Stable

Hire and offboard by contract

Contract-driven provisioning: usage location, licenses, groups, UPN convention. New hires and terminations become one reviewed action with a per-step result.

Stable

Find a user anywhere

Search every active tenant at once and go straight from a person to a fix. Tenants that can't be reached are listed, not hidden.

Beta

Known-fix workflows

MFA reset, password reset, compromised-account lockdown, and license repair. Each one shows its diagnosis, applies the fix step by step, then diagnoses again to confirm.

Beta

Mailbox archive repair

The "mailbox full / not archiving" fix that replaces about ten Exchange Online cmdlets, run through the EXO PowerShell V3 module out-of-process with an app-only certificate.

Beta

Config snapshots and diff

Captures of Conditional Access, Named Locations, and Device Compliance policies, diffable section by section or across the whole tenant, exportable, and optionally mirrored to a git repo. Read-only: there is no "apply to tenant".

Beta

Local accounts, passkeys and TOTP

Run without an external IdP: open registration, passkeys as the primary sign-in, optional TOTP with recovery codes, and per-tenant Viewer/Operator/Owner grants that even an Administrator can't bypass.

Beta

MCP server with human approval

LLM clients call seven tools at /mcp using a personal access token. A fix a client asks for is staged for a person to approve, unless that tenant is explicitly set to trust the client.

Planned

Two-way LDAP sync

Planned for a later phase and not implemented. This page will say so until it ships.

The workflow loop

Diagnose → Fix → Verify.

Every known-fix workflow follows the same shape, and every run is recorded: who ran what, against which tenant, with which findings. The record is there when you close the ticket.

1 DIAGNOSE

Read the real state from Graph or Exchange Online and show every finding as-is: Ok Info Warning Blocker. Nothing changes yet.

2 FIX

Apply the known remediation step by step, recording each step's result. Steps are idempotent, so re-running is safe; for the asynchronous mailbox move, re-running is the nudge.

3 VERIFY

Diagnose again right away and show the post-fix state, so "it should be fixed now" becomes "here is the state after the fix", saved to Postgres with the run.

Design principles

Non-invasive, transparent, auditable, self-hosted.

Non-invasive

No agents in customer tenants

The bridge calls the Microsoft Graph and Partner Center APIs under the Secure Application Model and each customer's GDAP relationship. No agent or service is installed downstream.

Transparent

Every step is shown

Diagnoses are shown as-is. Remediation steps are listed one by one with their outcome. A contract's plan is a dry run you can check before deploying.

Auditable

Every run is recorded

Workflow runs persist to Postgres with operator identity, inputs, findings, and steps. Failures can post a Teams Adaptive Card or plain JSON to a webhook.

Two auth planes

Who you are vs. what the bridge may do

Operators sign in through your OIDC provider or with self-registered Local accounts. The Microsoft plane is a separate SAM app with an encrypted, auto-rotating refresh token.

Contract model

Desired apps, planned per tenant

A contract is a named set of tenants and the apps they should have. The reconcile engine marks each tenant as deploy, update, retry, or nothing.

Self-hosted

Your credentials stay with you

Docker Compose for evaluation, Kubernetes (Kustomize + Flux + SOPS) for production. Secrets are encrypted at rest with ASP.NET Data Protection.

Integrations

The Microsoft services MSPs work in every day.

Tags show delivery status in the current build.

Core

Microsoft Graph

Per-tenant clients via GraphTenantClientFactory, powering Intune, users, groups, licenses, and the Identity workflows.

Stable

Partner Center API

Customer list sync and the Secure Application Model token flow via SamTokenService (MSAL), with automatic refresh-token rotation.

Stable

Intune Win32 apps

The full .intunewin upload sequence: content version, chunked block-blob upload, commit with parsed encryption info, then assign on first deploy.

Beta

Exchange Online PowerShell V3

Mailbox configuration Graph can't do, through the EXO module (app-only certificate) run out-of-process via PwshRunner.

Stable

Authentik / OIDC

Operator sign-in as a JWT bearer plane. Any standard OIDC provider works; set Auth and the matching VITE_OIDC_* variables.

Beta

MCP (Model Context Protocol)

Streamable HTTP server at /mcp, sharing tenant access, the workflow catalog, and the audit trail with the REST API. See MCP server.

Stable

Teams / webhook alerts

Failed runs post an Adaptive Card to a Teams incoming webhook, or plain JSON to any receiver, configured in the Notifications section.

Core

PostgreSQL

The source of truth via EF Core: tenants, contracts, templates, deployments, and workflow run history.

Planned

Two-way LDAP

Directory sync back to on-premises. Not implemented.

Try it locally

Click through the whole app with auth disabled.

The Compose stack runs Postgres, the API, and the web app with sign-in turned off, so you can explore every screen without an identity provider. Reaching real customer tenants also needs a partner Entra app and a one-time SAM bootstrap.

Operator plane - how you sign in. Use your own OIDC provider (JWT bearer), or Auth:Mode=Local for self-registered accounts: passkeys first, password as fallback, optional TOTP, and per-tenant sharing. The signed-in name is what run history records. Compose uses Dev mode, with no sign-in at all.

Authentication options

Microsoft plane - a multi-tenant Entra app under the Secure Application Model. SamTokenService exchanges the stored, encrypted, auto-rotated refresh token for a per-tenant Graph token on demand.

Reconcile engine - Core compares each contract's desired apps with what each tenant has and produces a plan you can review before deploying.

FAQ

Common questions.

Something missing? Open an issue on GitHub.

Is this a Microsoft product?

No. Partner Center Bridge is an independent open-source project from Spillers Technology. It is not affiliated with, sponsored by, or endorsed by Microsoft. Microsoft, Microsoft 365, Microsoft Entra, Intune, Exchange Online, and Partner Center are trademarks of the Microsoft group of companies.

Where does my data live?

On infrastructure you run. Tenants, contracts, templates, deployments, and run history are stored in your PostgreSQL database, and uploaded .intunewin packages in the API's package store. Secrets such as the SAM refresh token are encrypted at rest with ASP.NET Data Protection, using a key ring you keep on a persistent volume.

If you turn on the optional git sync, config snapshot captures are also pushed to the git repository you configure.

Does it install anything in customer tenants?

No agents or services. The bridge calls Microsoft Graph, the Partner Center API, and (for mailbox fixes) Exchange Online PowerShell, within the access your GDAP relationships allow.

It creates in a tenant only what you ask it to, such as the Intune Win32 apps you deploy. Each customer does need to consent to your multi-tenant app, as with any multi-tenant app.

Can I try it without a partner tenant?

Yes. The Docker Compose stack runs with sign-in disabled and no Microsoft credentials, so you can click through every screen. Acting in real tenants needs the partner app registration, GDAP, and the one-time SAM bootstrap.

What isn't done yet?
  • Two-way LDAP sync is planned and not implemented.
  • Win32 in-place update behavior is covered by tests against mocked Graph (WireMock), but has not yet been run against a live tenant.
  • The MCP server has no OAuth discovery flow yet; you mint a personal access token (Local mode) and give it to the client.
  • Known-fix workflows, mailbox repair, config snapshots, Local accounts, and the MCP server are Beta.
What's the license?

MIT. The source, issues, contributing guide, and security policy are on GitHub.
