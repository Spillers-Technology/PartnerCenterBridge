Docs / Get started

Local Workbench

A single self-contained PartnerCenterBridge.exe that embeds the API and the built SPA, stores its data in SQLite under your user profile, and runs with no server, no Postgres, and no external identity provider to stand up first. Everything else in the app -- workflows, operations, contracts, the audit trail -- is the same code path as the Server profile; only the hosting profile, the persistence provider, and the auth defaults differ.

First run, click by click

Start the exe, and it opens your browser to http://localhost:5080 once it's healthy. A brand-new install has no accounts yet, so GET /api/system/status reports needsFirstUser and the SPA sends you straight to registration -- there is no separate setup wizard to click through first.

The account you register here becomes the instance Administrator. Sign in afterward (a passkey once you've registered one, or your password) and Home is where you land: a person search, the four most common actions, and a Finish setting up card that only lists what still needs attention -- it disappears once every check is clean.

Each open check links straight to the screen that fixes it -- the same checks doctor and /settings/workbench report -- or, for the Exchange Online module, gives you the exact Install-Module command to copy and run. Nothing here is guessed at: a missing GDAP relationship, an unbootstrapped SAM connection, or a missing PowerShell module all show up by name, with their fix, instead of a generic "not configured."

Once a tenant is connected, every planned operation (mirroring access, offboarding) and every known fix ends at the same evidence view, whether you just ran it or you're opening it later from Activity or a person's History tab:

See Operations for the full walkthrough of mirroring access and offboarding, and below for what the first account and first launch actually do server-side.

Running it

PartnerCenterBridge.exe [command] [options]

Commands:
  (none)          Start the web app (API + UI).
  doctor          Check configuration and dependencies, print the results and exit
                  (exit code 0 = no errors, 1 = at least one error). Does not start the server.
  bootstrap-sam   Run the interactive Secure Application Model bootstrap (device code) and exit.

Options:
  --local             Use the Local Workbench profile. The Local Workbench build uses it by
                      default, so you will not normally need to pass it.
  --port <N>          Port to listen on (default 5080).
  --data-dir <path>   Data directory (default %LOCALAPPDATA%\PartnerCenterBridge).
  --listen <address>  Bind to another address instead of 127.0.0.1. Exposes the app to the
                      network; only use it when you understand the consequences.
  --no-browser        Do not open the browser after startup.
  --version           Print the version and exit.
  -h, --help          Print this help and exit.

Any --Section:Key=value argument is passed through as configuration.

On first launch the process creates its data directory, opens (and migrates) the SQLite database, prints a small banner with the URL and data path, waits for its own /health endpoint to answer, and then opens your browser there once. Stop it with Ctrl+C in that window.

Where data lives

Everything is under one data root: %LOCALAPPDATA%\PartnerCenterBridge on Windows ($XDG_DATA_HOME/PartnerCenterBridge, falling back to ~/.local/share/PartnerCenterBridge, on other platforms the same binary could run on), or wherever --data-dir points instead.

PathContents
pcb.dbSQLite database (tenants, contracts, workflow/operation runs, accounts, ...).
keys\ASP.NET Data Protection key ring -- DPAPI-protected on Windows. Encrypts the SAM refresh token and the local signing key.
auth-signing-key.protectedThe generated Auth:Local:SigningKey, itself protected with the key ring above.
logs\Rolling file logs.
packages\Uploaded .intunewin app packages.
certs\Where an Exchange Online app-only certificate (exo.pfx) is expected if you configure Exchange.
pcb.local.jsonOptional hand-edited config overrides, in ordinary appsettings JSON shape.

First launch and the first administrator

A fresh install has Auth:Mode=Local and no registered accounts. The first account you register becomes the instance Administrator -- there is no separate setup wizard. GET /api/system/status (anonymous, nothing sensitive) reports needsFirstUser so the SPA can send you straight to registration instead of a sign-in form that would otherwise fail with nothing to sign in to. The Local profile refuses to start at all with Auth:Mode=Dev -- that mode has no credentials, which combined with a bound network port would let anyone who can reach it act as administrator.

Second launch and port collisions

Before binding its port, the Local profile checks what is already there. If the port already answers as this app -- verified by calling its /api/system/status and checking for the X-PCB-Instance: PartnerCenterBridge response header, not just "a port is listening" -- it opens your browser to that existing instance and exits 0, so double-launching (or a shortcut that starts it every time) is harmless. If the port belongs to something else, it fails with an actionable error instead of trying to bind anyway. IPv6 is checked too: because browsers resolve localhost to ::1 first, something already listening on [::1] would otherwise shadow a successful IPv4 bind.

The canonical origin

Passkeys are bound to one origin, so the Local profile has exactly one: http://localhost:<port>. A request addressed to a loopback IP literal (127.0.0.1 or [::1]) is redirected there for GET/HEAD, or rejected with 421 Misdirected Request for anything else -- silently replaying a request body at a different origin is not something a client should rely on. This only normalizes which host a request is answered on; it grants nothing, and no request is trusted for being local (see below). See Authentication for how this interacts with WebAuthn's relying-party id.

Diagnostics: doctor and /api/system/diagnostics

doctor runs the same checks as GET /api/system/diagnostics (full detail there too -- whoever can run the binary already has its configuration) and prints each one with a suggested fix command and/or an SPA route to open, then exits 1 if any check is an error. A signed-in caller who is not an instance Administrator gets only the capability flags (graph, exchange, partnerCenter), not the check detail.

Check idWhat it verifies
hostingProfile and version; warns if bound to a non-loopback address.
databaseCan connect; applied vs. pending migrations.
data-protectionKey ring folder exists, is writable, and holds at least one key.
authLocal: user/administrator counts. Dev: warns it is not for shared use. Oidc: authority configured.
samPartner app configured, and whether SAM has been bootstrapped or a seed token is set.
tenantsAt least one active tenant onboarded.
pwshPowerShell 7 found on PATH (or Exchange:PwshPath).
exchange-moduleThe ExchangeOnlineManagement module installed for that pwsh.
exchange-appExchange app id configured and the app-only certificate present on disk.

Exchange Online as an optional dependency

Mailbox operations (mailbox archive repair, offboarding's mailbox conversion and forwarding) need three things that nothing else in the app requires: pwsh on PATH, the ExchangeOnlineManagement module installed for it, and an app-only certificate configured (Exchange:AppId + Exchange:CertificatePath, which defaults to certs\exo.pfx under the data root). Everything else works without any of it. When a piece is missing, the affected section reports Unavailable with the specific reason instead of a silent no-op -- the person workspace's mailbox section, and any offboarding item that needs Exchange. doctor and the diagnostics endpoint probe pwsh and the module out-of-process (cached 60 seconds so repeated checks stay fast) and the certificate fresh every time, and report the first missing piece in the order you'd actually fix them.

Protecting secrets and data

  • DPAPI-protected key ring -- the Data Protection key ring under keys\ is encrypted at rest for the current Windows user (ProtectKeysWithDpapi), in addition to ordinary file-system persistence. It protects the SAM refresh token and the local signing key. Losing it, or moving the data directory to another user account, makes those secrets undecipherable -- the sam and data-protection checks say so rather than failing silently.
  • Protected signing key -- Auth:Local:SigningKey is generated once (256 random bits) and stored encrypted with that same key ring at auth-signing-key.protected. Every restart reuses it; deleting the file (or the key ring) rotates it and signs everyone out.
  • User-only ACLs -- a data directory this process creates (not one you point --data-dir at) gets its Windows ACL restricted to the current user plus SYSTEM, best-effort. A failure to restrict it is a startup warning, not a hard failure, since %LOCALAPPDATA% is already per-user.
  • Defense in depth on the network side -- loopback-only Kestrel binding, the canonical-origin middleware, and AllowedHosts pinned to exactly localhost;127.0.0.1;[::1] (plus an explicit --listen address, when given) all apply together, so a DNS-rebinding host cannot reach the app even if it tricked a browser into resolving a public name to loopback.
  • No localhost auth bypass -- none of the above is authentication. Loopback binding and the canonical-origin check only normalize which origin a request lands on; every request still goes through the same Auth:Mode=Local sign-in as any other deployment. There is no special-cased "requests from 127.0.0.1 are trusted" path.

Building it

./scripts/publish-local.ps1 (.NET 8 SDK + Node.js/npm) builds the SPA (npm ci + npm run build, unless -SkipSpaBuild is given, in which case an existing web/dist is embedded as-is) and publishes a single-file, self-contained, trimmed-symbols exe to artifacts/local/win-x64/PartnerCenterBridge.exe. Equivalent command: 

dotnet publish src/PartnerCenterBridge.Api -c Release -r win-x64 --self-contained `
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:EnableCompressionInSingleFile=true -p:DebugType=embedded -p:PcbLocalWorkbench=true `
  -o artifacts/local/win-x64

.github/workflows/ci.yml runs this on every PR and push to main (Windows runner), then smoke-tests the published exe: health check, the /api/system/status profile, the SPA fallback for a deep link, loopback-only binding, and a stop/restart to confirm pcb.db persists. It also runs doctor non-gating (Exchange and SAM are expected unconfigured in CI) and uploads the exe as a 14-day build artifact.
